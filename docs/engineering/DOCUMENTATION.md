# 文档规划与维护约定

[文档中心](../README.md) · [工程入口](README.md)

本次整理目标：让新读者能够找到“这是什么、怎样运行、怎样使用”，让维护者能够找到唯一的规范、当前状态和历史证据。保留已批准基线及原始验证记录。

## 内容分层与唯一来源

| 层次       | 位置                                   | 放什么 / 不放什么                                          |
| ---------- | -------------------------------------- | ---------------------------------------------------------- |
| 项目门面   | 根 `README.md`                         | 定位、功能概览、截图、启动摘要、导航；不堆完整验收日志     |
| 操作指南   | `docs/guides/`                         | 当前可执行的安装、使用和排障；不写某台机器的临时授权状态   |
| 产品规范   | `docs/product/`                        | PRD、决策、故事与 AC；不靠完成勾选替代真实证据             |
| 技术规范   | `docs/architecture/`、`docs/adr/`      | 当前契约和决策理由；生成文件不手改                         |
| 工程流程   | `docs/engineering/`                    | 开发规则、测试策略、迁移审核与任务计划                     |
| 设计与证据 | `docs/ux/`、两处 `evidence/`           | 设计、原型、每轮测试结果及图像；设计原型与真实验证分别标注 |
| 项目状态   | `docs/STATE.md`、`docs/HUMAN_TASKS.md` | 已验证里程碑与人工事项；不作为产品规范的替代               |
| 发布与调研 | `docs/release/`、`docs/research/`      | 发布门槛、调研材料；不将调研假设描述成已验证结论           |
| 子应用说明 | `apps/*/README.md`                     | 该包职责与特殊操作；通用安装链接到运行指南                 |

产品承诺以已接受决策 / PRD / ADR 为准；行为契约以状态机、数据模型和 API 为准；运行命令以实际脚本为准；实施状态与测试结论必须注明日期、环境和证据。发现实质冲突时先记录并交负责人确认，不用整理文档的机会更改基线。

## 后续整理顺序

以下是后续可独立评审的整理步骤，**本次尚未移动这些历史文件**。现有路径保留，避免破坏 GitHub Issue / PR 引用、代码生成输出和测试证据路径。

1. **精简 STATE**：把已完成交接按阶段拆入拟建的 `docs/history/`，保留日期、提交引用、原始命令、失败和 NOT RUN。STATE 只保留当前摘要、近期里程碑、下一步和历史索引；旧章节锚点保留跳转入口。
2. **拆分 DEVELOPMENT**：把 R01–R08 的机器故障、临时覆盖命令和当时的授权说明归入对应历史记录；通用安装只维护运行指南，仍保留原有本机演示 / 迁移章节入口。
3. **归集已结束任务**：待对应阶段稳定后，将阶段计划、检查点、PR 草案归入历史目录；SQL 审核包及证据优先保留原位，以链接串联。不要单独移动 SQL、snapshot 或 journal。
4. **检查引用后再移动**：先用 `rg` 查仓库引用和生成器 / 测试脚本；迁移时更新相对路径，旧入口保留指向新位置的说明，复核所有链接与锚点。

完成上述步骤后，日常入口应无需阅读历史记录即可使用；历史结论仍可定位到原有版本、环境和证据。归档不代表废弃已接受的产品决策。

## 命名与状态

- 指南按任务命名，如 `GETTING_STARTED.md`、`USER_GUIDE.md`；目录用小写，稳定文档沿用仓库现有大写文件名。
- 新增阶段记录应包含阶段编号或日期，并在工程索引登记；避免继续新增 `FINAL`、`LATEST`、`NEW` 等含糊文件名。
- 规范注明版本与接受状态；操作指南说明适用环境；阶段记录注明日期、代码范围、执行环境、结果与未运行项目。
- 历史文件不改写当时的结果。用顶部说明或索引指出后续替代记录，不能将早期“未迁移”直接解释成当前环境仍未迁移。
- 临时完整输出写入被忽略的 `test-results/`；有价值、已脱敏的交接证据再进入 `evidence/`，不提交凭据、会话存储或客户原件。

## 什么时候更新哪些文档

| 变更                         | 同步位置                                                             |
| ---------------------------- | -------------------------------------------------------------------- |
| 安装、环境变量、运行命令     | `.env.example` / 实际脚本、运行指南；README 中出现的摘要同步核对     |
| 用户操作或可见功能           | 使用指南；首页功能概览只在对外介绍变化时更新                         |
| API / 数据 / 权限 / 状态转换 | 对应契约、验收标准、必要 ADR 和生成产物；先取得需要的产品 / SQL 审核 |
| 已验证里程碑                 | STATE 的简短摘要 + 对应证据链接；人工事项写 HUMAN_TASKS              |
| 新文档或归档                 | 文档中心或工程索引，以及指向它的相对链接                             |
| 发布                         | 发布检查表、状态与经过验证的发布说明                                 |

## 文档变更的完成标准

1. 新读者从首页两次跳转内能找到安装、使用、契约或当前状态。
2. Markdown 链接、图片、标题锚点可用；命令对应实际脚本，版本与端口来自仓库配置。
3. 当前指南不依赖某台开发机的绝对路径、临时脚本、预置账号或隐藏配置。
4. 保留人工审批、不可变版本和角色隔离语义；不将本地验证写成生产发布。
5. Review 时说明实际完成的文档检查；纯文档调整不声称重新通过了业务回归。
