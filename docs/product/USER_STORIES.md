# SpecBridge 用户画像、场景与用户故事

> v0.2 需求基线。以下人物为**假设画像**，不是已访谈用户。

## 角色画像

- **Owner／小型工作室负责人**：同时维护多个客户项目，痛点是范围变动引发额外沟通与费用争议；关键操作：建立项目、邀请成员、确认商业影响。
- **Developer／独立开发者**：希望知道当前可执行的是哪个需求版本；关键操作：梳理要求、评估工时、交付和处理退回。
- **Client／项目委托方**：不熟悉技术术语，只关心做什么、什么时候完成、是否符合预期；关键操作：提要求、回答问题、批准、验收。

## 具体场景

**S1：新增积分功能**。客户提交“会员有积分，积分抵扣订单”；需要问清来源、抵扣比例、退款回滚、上限；开发者评估范围与工期；双方批准；交付时按已批准的验收标准核对。

**S2：客户变更已确认需求**。已经批准的是“积分不可过期”，客户现在希望 30 天过期。系统不能把历史版本改成 30 天，而应新建需求版本/变更评估并重新审批。

**S3：两位客户隔离**。A 项目 Client A 登录后，不能通过修改浏览器 URL/请求参数查看 B 项目的需求、报价或交付。

**S4：AI 故障**。DeepSeek 超时，Developer 仍可手动创建澄清问题和变更流程，主业务不受影响。

## 关键用户旅程：US-07 → US-11

1. 前置：最新 RequirementRevision 为 Ready；Developer 有项目权限；项目恰有一个已注册 Client。
2. Developer 输入 `scope_summary`、`estimate_hours`（≥0）、`cost_delta_minor`（可为 0）、`currency`、`schedule_delta_days`（可为 0）、`acceptance_criteria`。
3. 预览不可变 `ChangeRequestVersion`，提交审批；Owner 查看并批准。
4. Client 看到**同一**版本及完整影响后批准；系统记录批准的准确版本。
5. Developer 可创建 Delivery；Client 接受或退回。
6. 如果变更重新提交，之前版本的批准不可移植到新版本。

## 前端需要覆盖的状态

- 空项目、空需求列表；Loading；保存成功与失败反馈；表单无效字段；无权限；版本冲突提示与重新加载；AI 超时与重试；审批中/审批通过/退回；交付为空/审核中/已验收。
- Owner、Developer、Client 三类账号均有可走通的起始入口，不只是顶部菜单差异。

## 待验证问题

- 客户是否愿意注册并登录独立门户，而不是继续使用 IM？
- 小团队最担心的是需求歧义还是报价/工期争议？
- “双重审批”是否形成过高的点击成本？
- 是否存在已有可替代的工具组合？

这些问题需要真实访谈；界面和故事不能充当验证结果。

## 冻结补充场景（v0.2）

- **US-16（P0）**：Owner 可创建未绑定 Client 的项目，但在首个正式变更提交前必须指定唯一已注册客户；未经绑定提交应返回 422。
- **US-17（P0）**：Owner 在项目尚未发生正式提交前可更正客户绑定；第一次提交后不得经公开 v1 API 更换客户（409）；同 Workspace 供应方账号不能作为 Client。
- **US-18（P0）**：任何人无法更改创建时的 `baseline_scope`；提交额外范围时可对照初始参考说明，但平台不把该说明冒充已签署合同。
- **US-19（P0）**：一个需求已有审批中的变更版本时，开发者不能产生新 RequirementRevision；拒绝或通过后可再产生新 Revision / 新 CR，不篡改旧记录。
- **US-20（P0）**：客户退回某次 Delivery 后，开发者可以提交新的 HTTPS 交付链接；同一个已批准版本不能存在两个待审 Delivery；完成 Accept 后不能继续提交。

后续 GitHub Issues 应引用这些故事与 `docs/product/ACCEPTANCE.md` 中的 AC-22～AC-27。
