# SpecBridge 产品需求文档（PRD）

> 版本：v0.2（需求基线）｜日期：2026-11-01｜状态：**D-01 至 D-04 已确认；P0 范围冻结，待实现验证**  
> 用途：确定 MVP 业务边界；不代表已实现或经过真实市场验证。  
> 变更原则：若改变已冻结的 P0 业务边界，先修订 PRD + ADR + 验收编号；普通产品需求变更走 ChangeRequest。

## 1. 产品概要

2026-11-13增量批准：负责人确认“项目背景、分步澄清、可确认执行的助手、Codex接入”方案并授权实施，见 [AI工作流升级](../engineering/AI_WORKFLOW_PLAN.md) 与D-09。以下v0.2的P0审批/不可变历史/链接交付基线继续有效；文件上传仅为新背景资料功能，不扩展为交付附件。原FR-14的文件限制及R08只读Copilot是历史范围，按新计划分阶段增量交付，不能把批准设计当作已实现。

**一句话定位**：SpecBridge 是面向独立软件开发者及小型开发工作室的 AI 原生「客户需求澄清—范围变更确认—交付验收」协作产品。

### 用户问题（**待访谈验证的假设**）
- 客户以自然语言提出不完整/模糊需求，开发者往往直接实施；澄清问题散落在微信、邮件、IM。
- 开发中出现新增范围，双方缺少与**确定需求版本**绑定的时间、工作量/费用/工期评估和批准记录。
- 提交成果后的验收标准和实际批准的版本脱节，争议、返工不易追溯。
- AI Coding Agent 缩短编码时间，但不能自动决定客户真实意图或商业范围。

### Job to be Done
> 当客户提出新需求或修改已有范围时，开发团队希望用少量操作把意图澄清并冻结成双方认可的版本，在交付时能够依据该版本验收，减少误解与返工。

## 2. 客户、角色与使用边界

| 角色 | 目标 | v1 权限边界 |
|---|---|---|
| Workspace Owner（供应方负责人） | 管理工作空间、项目、范围和商业审批 | 能管理所在工作空间；供应方审批只有 Owner |
| Developer（开发者） | 澄清、评估、跟踪需求和提交交付物 | 仅限被分配项目；不得替客户/Owner 批准 |
| Client（客户审批人） | 提需求、回答澄清、确认范围、验收 | 仅能访问被绑定项目，不能读取内部数据 |

**MVP 已确认**：项目创建时允许尚未绑定 Client；**进入首个变更审批前必须绑定且仅绑定一个已注册 Client 审批账号**。同一 Client 账号可被分配到多个不同项目。Owner 管理本 Workspace 的所有项目；Developer 需经项目分配。Client 不加入供应方 Workspace；一个供应方账号不能在同一 Workspace 项目担任 Client。首次正式提交变更后，v1 不支持更换客户审批账号，避免审批身份漂移；创建前的误分配可以由 Owner 改正。邮箱邀请和密码找回不在 MVP 内。

## 3. 差异化定位

现有客户门户（如 ManyRequests）已有请求、文件、审批和权限，项目管理产品也能处理范围/验收。SpecBridge **不宣称首创这类功能**。首版差异化集中在：
1. **需求版本中心**：所有商业审批、交付都指向一个不可变的规格版本。
2. **澄清与事实分离**：AI 草稿以 `assumptions/open_questions/acceptance_criteria` 形式给建议，不静默改变原文或业务记录。
3. **面向软件开发的可执行规格**：未来 MCP/Skill 可读取“已批准”的版本；禁止工具直接审批。

商业效果必须通过访谈和真实使用验证，不能将上述设计目标写成已证明的竞争优势。

## 4. 业务对象与范围

- **Workspace**：供应方团队空间。
- **Project**：客户软件项目，Owner 创建时写入非空 `baseline_scope`，作为**不可编辑的初始参考快照**。这是供应方录入的已知范围，**不等于双方在 SpecBridge 内签署的初始合同**；v1 没有初始范围签认步骤。后续提出的需求及变更以该范围为比较依据；产品只追踪经过 ChangeRequest 确认的正式交付，不替代原项目全部任务管理。
- **Requirement**：客户问题/需求主体，可在 `Draft → Clarifying → Ready` 中流转。
- **RequirementRevision**：不可变的结构化需求版本（正文、验收标准、已澄清问题），在新版本生成后不修改旧版本。
- **ChangeRequest**：由 Owner/Developer 对一个最新 Ready RequirementRevision 发起正式评估，包含**可编辑草稿字段**：关联的需求版本、范围说明、预计工时、费用增量（可为 0）、币种、工期变化（可为 0）、验收标准。即使是原范围内的澄清，若需要在平台完成正式批准与交付，也通过零费用/零工期增量的变更单走闭环。
- **ChangeRequestVersion**：提交时冻结商业影响与需求版本的不可变快照。修改或拒绝后重新提交，生成新版本；原审批不沿用。
- **Approval**：针对确定 ChangeRequestVersion 的供应方/客户批准或拒绝决定。
- **Delivery**：针对已批准 ChangeRequestVersion 的交付记录（说明、URL、验证证据）。退回时新建交付记录，不覆盖旧记录。
- **DeliveryReview**：客户对某次交付的通过或退回记录。
- **AuditEvent**：关键操作不可随业务内容修改而被抹去的审计事件。

## 5. 主流程（Happy path）

1. Owner 建立 Workspace 和 Project，写入不可编辑的初始范围参考快照、分配 Developer，并在**首次 Submit 前**绑定唯一 Client 账号。
2. Client 创建 Requirement 草稿；提出描述与期望。
3. Client/Developer 通过问题澄清；按需调用 AI 生成建议，经人审核后形成 Revision，并标记 Ready。
4. Developer 针对最新 Ready Revision 创建 ChangeRequest Draft，填入范围、工作量、工期影响、费用增量（含币种）；非负预计工时、可正负/零的费用增量，所有金额增量均按整数最小货币单位存储。
5. Developer 提交 ChangeRequestVersion；Owner 批准供应方评估；Client 查看同一冻结快照后批准。
6. Developer 实施后针对已批准版本提交 Delivery（结果链接、说明、测试证据）。
7. Client 验收通过 → 流程完成；或退回并给反馈 → Developer 创建新的 Delivery。
8. 全流程保留操作人、时间、关联版本以及可查历史。

### 错误/异常路径
- 未就绪或非最新需求版本不得提交变更；没有唯一 Client 账号不能提交；已提交的变更版本不可就地修改。**同一 Requirement 存在 SUBMITTED 或 VENDOR_APPROVED 的审批时，禁止生成新 Revision（409）**；待当前版本被批准或拒绝后再提出新的修订。
- Owner/Client 任一方拒绝后，该版本终止；新一轮提交必须创建新 ChangeRequestVersion。
- 过期 `lock_version` 返回 409；重复审批不能产生双重决定。
- AI 失败、超时、非法 JSON 时保留原始需求、允许手动填写。
- 客户跨项目访问返回 404（减少资源存在性泄露），未认证返回 401。

## 6. 功能需求与优先级

| ID | 功能需求 | 优先级 | 可验收结果 |
|---|---|---|---|
| FR-01 | 注册、登录、退出、服务端 Session | P0 | 两种账号在独立浏览器登录且退出会话失效 |
| FR-02 | Workspace、Owner/Developer 成员管理 | P0 | Owner 管理供应方成员；非 Owner 不可管理 |
| FR-03 | Project CRUD、开发者与单客户分配 | P0 | 各用户只看到获授权项目；初始范围可见 |
| FR-04 | Requirement CRUD 和澄清状态 | P0 | 保存原文、问题/答复，状态合法转移 |
| FR-05 | 不可变 RequirementRevision | P0 | 历史版本可查，旧版不能覆盖 |
| FR-06 | ChangeRequest 评估及冻结版本 | P0 | 对最新 Ready Revision 生成固定商业快照 |
| FR-07 | 供应方和客户依次审批/拒绝 | P0 | 审批绑定版本；重复操作无冲突副作用 |
| FR-08 | Delivery 和客户验收/退回 | P0 | 最终通过或保留退回历史 |
| FR-09 | AuditEvent、基础检索与状态概览 | P0 | 关键业务操作可追溯；简洁 Dashboard |
| FR-10 | 安全、数据隔离、CI、正式部署 | P0 | P0 验收测试通过；HTTPS 可用 |
| FR-11 | DeepSeek 辅助澄清/验收标准 | P1 | 人工可编辑建议；模型故障不阻塞主流程 |
| FR-12 | 只读 MCP + Requirement Skill | P1 | Agent 只能按授权读取已批准规格 |
| FR-13 | GitHub Issue 链接 | P1 | 保存 Issue URL；不强求自动双向同步 |
| FR-14 | 多客户审批、文件上传、支付、实时消息 | P2 | v1 不做 |

## 7. 页面信息架构（v1）

- `/login`、`/register`
- `/app`：Workspace/项目列表、待办统计
- `/app/projects/[id]`：范围、成员、需求列表
- `/app/projects/[id]/requirements/[requirementId]`：原文、澄清、版本、创建评估
- `/app/projects/[id]/changes/[changeId]`：冻结范围/影响、双方审批、审计
- `/app/projects/[id]/deliveries/[deliveryId]`：交付内容、客户验收
- `/app/settings/members`：仅 Owner 管理工作空间成员

低保真原型见 `docs/ux/WIREFRAMES.md`。

## 8. 非功能需求（设计目标，非现有测试结果）

| ID | 要求 | 首版验收 |
|---|---|---|
| NFR-01 | 租户隔离 | 关键资源 API 中跨项目读/写均不能成功 |
| NFR-02 | 审批一致性 | 事务 + 唯一约束 + 并发冲突测试 |
| NFR-03 | 应用安全 | 基线检查依照 OWASP ASVS 5.0 的相关 L1 类别，记录不适用项 |
| NFR-04 | 响应性 | 在演示数据（≤20 项目、≤200 需求）及本地单用户条件下非 AI 列表 API p95 ≤800ms（目标） |
| NFR-05 | AI 可用性隔离 | 模型失败不影响 P0；错误可见；不记录密钥 |
| NFR-06 | 部署与恢复 | HTTPS、环境隔离、数据库卷持久化、一次备份恢复演练 |
| NFR-07 | 可追踪 | 关键状态变更写审计；请求日志不含敏感正文/密码/Token |
| NFR-08 | 开发过程 | PR/CI、可复现迁移、README、E2E 证明主链路 |

## 9. 范围外（Non-goals）

不做付款结算/合同电子签章、客户多人分级审批、专业 CRM、智能工时预测、全量文件管理、完整聊天工具、实时多人协作、移动原生 App、对外开放的远程 MCP/OAuth 平台、AI 自主接受或拒绝范围变更。不将演示数据/模拟访谈当作真实用户证据。

## 10. 成功指标（上线后待测）

- 最低要求：一个真实或明确标记的演示项目从需求到验收完整走通；P0 阻断缺陷为零。
- 产品假设验证：采访 3–5 位实际接单者/小团队开发者；至少 2 人试用；记录实际痛点和使用障碍。
- 初步行为指标：需求创建→确认的中位耗时、被退回需求比例、每次审批历史可回溯率；小样本不对外宣传统计改善。

## 11. 依赖、风险与取舍

| 风险 | 缓解 |
|---|---|
| 客户端引入流程过重 | 一项目一审批人；表单默认字段尽量少，允许金额增量为 0 |
| 两周工期失控 | P0 全链路优先，P1 不阻断发布 |
| 没有真实用户 | 先约访谈；在文档注明假设，不能冒称已验证 |
| AI 建议误导 | 原文保留、AI 标签、人审确认、Schema 校验 |
| 跨项目数据泄露 | 服务端授权、负向权限测试、日志脱敏 |
| 范围与版本混乱 | 不可变快照、审批引用版本、乐观锁、事务 |

## 13. 已批准的 P0 业务不变量（冻结）

1. 一个项目在创建时可没有 Client，但首个 `ChangeRequest.submit` 前必须且只能有一个有效 Client；一旦提交过正式审批，v1 不提供客户账号替换操作。
2. 客户账号不能兼任同一 Workspace 的供应方 Owner/Developer；供应方成员只能访问有权限的项目。
3. `baseline_scope` 创建时要求非空、创建后不可覆盖；它是供应方录入的参考快照，**不提供初始合同电子签署或初始范围正式审批**。
4. 从 Draft 到正式交付的跟踪链路为 `RequirementRevision → ChangeRequestVersion → Approval → Delivery → DeliveryReview`，版本皆可追踪。
5. 每个 ChangeRequestVersion 都严格先 Owner 后 Client 批准，任何拒绝都终止当前版本；新一轮审批必须生成新快照。
6. 交付仅支持 HTTPS 成果 URL + 文本说明 + 可选 HTTPS 证据链接，不上传文件；交付关联已批准版本，退回后创建新一轮交付。
7. AI、MCP、GitHub 集成均不参与 P0 的商业审批；AI 故障不阻塞业务闭环。
8. 对已批准规格新增需求时应创建新 Revision 和**新的 ChangeRequest**，旧批准和旧交付保留可查；不擅自使历史交付失效。

> **注意**：“需求范围已确定”指产品负责人确认的设计范围，不等于产品已有真实用户验证，也不等于已实现。
